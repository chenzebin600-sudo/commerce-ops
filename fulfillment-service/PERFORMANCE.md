## 并发 2 的真实验收标准

至少取得一个包含 2 单或以上的真实批次，并同时满足：

- 批次 `timings.orderConcurrency` 为 `2`。
- 全部订单成功，均取得运单号且最终状态为“配货中”。
- 无登录失效、渠道不匹配、库存未知或幂等冲突。
- 两单波次的批次执行耗时明显小于两单 `executorTotal` 之和，证明等待阶段确实重叠。
- 任一波发生失败时，后续波次不会启动；此行为由自动化测试覆盖，真实环境不主动制造失败验证。

上述验收标准已经满足。并发上限继续固定为 2，不提高到 3 或更高；后续优化继续围绕扫描开销、进程登录开销和只读轮询效率展开，不删除或缩短安全检查。

## 持续监控规则

- 每天优先观察包含 2 单以上的自然真实批次，不为性能测试主动制造失败或重复发货。
- 记录批次成功率、订单成功率、`preSubmitRevalidation`、`trackingWait`、`distributionWait` 和多单提速倍数。
- 任一批次出现 `partial_success`、`failed` 或 `needs_attention` 时，先停止继续提速并检查具体安全错误。
- 只有 `scheduler.scanning=false` 且 `activeBatch=null` 时才允许计划内重启。
- 没有代码或配置变更时不为“验证”额外重启稳定服务。

## 多店铺扫描提速（2026-07-29）

旧实现对 5 个店铺逐店登录、逐店导出相同日期范围，再在本地筛选店铺。真实定时扫描通常约 70—90 秒，主要是同一账号数据被重复采集。

新实现一次登录并完成账号级只读采集，然后按配置中的店铺 ID/名称把记录隔离给各店铺预览。真实部署后的第一轮自然定时扫描结果：

| 指标 | 结果 |
| --- | ---: |
| 扫描策略 | `shared_account_scan` |
| 共享采集耗时 | 14.298 秒 |
| 整轮扫描耗时 | 14.351 秒 |
| 相对旧版 | 约 5 倍提速 |
| 扫描后真实批次 | Toko Penguin，1 单 |
| 批次结果 | 成功取得运单号并转入“配货中” |
| 批次总耗时 | 37.676 秒 |

部署前还在同一安全窗口对 JOJO Mall 执行旧单店读取与新共享读取对照：两者均返回 5 行明细，匿名差异集合为 0。新方案仅优化只读候选采集；确认后的整批复检、逐单提交前复检、交运请求、运单号回查、渠道核对和转配货逻辑均未修改。

共享采集出现登录、网络或响应错误时，调度器记录 `per_shop_fallback` 并自动使用原逐店读取。不得因追求扫描速度取消该回退，也不得把共享只读快照直接当作真实提交依据。
