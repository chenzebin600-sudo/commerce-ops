# Commerce Ops PostgreSQL F0 安装准备审计与迁移实施方案

## 1. 审计范围与结论

本报告对应 F0，只进行了系统、端口、项目、备份和正式 SQLite 的只读检查，并设计后续实施方案。F0 没有下载或安装 PostgreSQL，没有启动安装器，没有创建 Windows 服务、数据库或账号，没有安装 Node PostgreSQL 驱动，没有修改正式 `.env.local`、SQLite、业务表结构或业务代码，也没有执行导入或双写。

**最终状态：`MANUAL_ACTION_REQUIRED`**

当前 Windows、硬件、磁盘、服务管理器和网络条件满足 PostgreSQL 原生安装要求，未发现技术阻塞。状态不是 `READY_FOR_INSTALLATION` 的唯一原因是：当前终端不是管理员会话，而 Windows 安装和服务注册需要用户手工批准 UAC；安装器还要求用户自行设置 `postgres` 管理员密码。完成这两项人工动作后，可以进入 F1。

### 类型映射

- UUID 形式的 `TEXT` 主键 -> PostgreSQL `uuid`。
- 自增 `INTEGER PRIMARY KEY AUTOINCREMENT` -> `bigint GENERATED BY DEFAULT AS IDENTITY`。
- ISO 时间文本 -> `timestamptz`；纯业务日期 -> `date`。
- `*_json` 文本 -> `jsonb`，导入前逐行验证 JSON。
- 0/1 整数标记 -> `boolean`，导入前确认值域仅为 0/1。
- 文件字节数和累计计数 -> `bigint`。
- 状态值第一版继续使用 `CHECK`，暂不引入 PostgreSQL enum。

### SQLite 特有语法

需要在 F2 Provider 中适配：`PRAGMA`、`BEGIN IMMEDIATE`、`INSERT OR IGNORE`、`datetime('now')`、`AUTOINCREMENT`、`?` 占位符、JSON 文本和 0/1 布尔。SQLite 的 `ON CONFLICT` 语义、部分唯一索引、外键删除动作和调度租约原子性必须逐项保留，不能做字符串级机械替换。

### 迁移量与预计耗时

当前数据不足 1 MiB、486 行，纯数据复制通常可在 1 分钟内完成。正式演练应预留 15-30 分钟，用于建表、导入、主键/外键/唯一约束验证、逐表对账和文件元数据哈希核验。耗时风险主要来自校验流程，不是数据量。

当前数据库尚未持久化标准化订单、订单明细、库存快照、竞品快照、关键词结果、广告指标或 AI 分析结果；这些未来业务表不应混入本次 SQLite 原样迁移。

## 6. 当前备份与恢复能力

节点 D2B2B 的 C、D 双盘备份仍存在且可访问，均包含 manifest、正式文件清单、一致性 SQLite 备份和原始 SQLite 快照。两套 manifest 与 SHA-256 核验一致，一致性数据库的 `PRAGMA integrity_check` 均为 `ok`。F0 没有创建新备份，因为未发现现有备份损坏，也没有写入正式数据。

后续关键检查点：

1. F1 安装前复核 Git、端口、C/D 备份和正式 SQLite integrity。
2. F3/F5 前停止所有写入服务，执行 WAL checkpoint，并用 SQLite backup API 或 `VACUUM INTO` 生成一致性副本。
3. 同时保留主文件、WAL、SHM 原始快照和文件存储 manifest。
4. PostgreSQL 从 F3 起使用自定义格式逻辑备份，例如 `pg_dump -Fc`，并用 `pg_restore --list` 验证可读性。官方文档说明自定义格式适合由 `pg_restore` 选择性、并行恢复：[SQL dump / custom format](https://www.postgresql.org/docs/current/backup-dump.html)、[pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)。
5. 正式切换前后保存逐表对账结果、配置备份和回滚负责人。

## 7. 安装方式比较

| 维度 | Windows 原生安装 | Docker Desktop + PostgreSQL |
|---|---|---|
| 用户操作难度 | 安装向导直观，适合当前使用者 | 需先安装 Docker、理解容器和卷 |
| 自动启动 | Windows 服务原生支持 | 依赖 Docker Desktop 和容器启动策略 |
| 资源占用 | 较低 | 多一层 Docker/虚拟化资源 |
| 备份恢复 | 直接使用 `pg_dump`/`pg_restore` | 同样使用工具，但还需管理卷 |
| 换电脑迁移 | dump + 文件备份即可 | 镜像可复用，但卷仍需迁移 |
| 未来迁云 | dump/restore，与云 PostgreSQL 兼容 | 容器不等于托管云数据库，仍需 dump/restore |
| Node/Python/Chrome | 本机回环连接最直接 | 需处理容器到宿主机网络 |
| 当前电脑现状 | 无冲突，可直接规划 | Docker 未安装，会扩大 F1 范围 |

**推荐：Windows 原生安装 PostgreSQL。** PostgreSQL 官方 Windows 下载页提供 EDB 交互式安装器，包含服务端、pgAdmin 和 StackBuilder；官方也建议在有二进制包时优先使用二进制安装：[Windows installers](https://www.postgresql.org/download/windows/)、[Binary installation](https://www.postgresql.org/docs/current/install-binaries.html)。

## 8. F1 安装参数建议

以进入 F1 当天 PostgreSQL 官方支持列表中的最新当前小版本为准。按本次审计日期，建议 **PostgreSQL 18.4 x64**：18 是当前主版本且支持期最长；官方当前版本和支持周期应在下载当天再次核对：[Versioning policy](https://www.postgresql.org/support/versioning/)。

逐屏建议：

1. **安装包**：仅从 PostgreSQL 官方 Windows 下载页进入 EDB x64 安装器。
2. **安装目录**：`%ProgramFiles%\PostgreSQL\18`。
3. **组件**：勾选 PostgreSQL Server、Command Line Tools；pgAdmin 建议安装，便于当前使用者只读查看；取消 StackBuilder，本项目不需要额外扩展。
4. **数据目录**：D 盘根目录下的 `PostgreSQL\18\data`，不要放入项目目录、同步盘或备份目录。
5. **管理员密码**：由用户现场生成并保管高强度唯一密码；报告和代码不提供示例真实值，不复用 `APP_ACCESS_TOKEN` 或马帮密码。
6. **端口**：5432。
7. **Locale**：安装器使用 `Default locale`；安装后验证 `server_encoding = UTF8`。业务数据库时区统一设置 UTC，前端按店铺/用户时区显示。
8. **服务**：保留安装器创建的 Windows 自动启动服务；不改服务账号，不手工创建第二个服务。
9. **不勾选/不执行**：StackBuilder、远程访问、防火墙 5432 入站、第三方扩展、样例数据库导入、项目数据导入。
10. **完成验证**：检查服务状态、`psql --version`、`pg_dump --version`、5432 仅回环监听、`SHOW server_encoding`、`SHOW TimeZone`、`SHOW password_encryption`，并确认 Commerce Ops/广告端口未受影响。

F0 只规划，不创建：

|---|---|---|
| 正式数据库 | `commerce_ops` | 后续正式切换目标，F1 不导入业务数据 |

建议数据库由 `postgres` 管理，`app` schema 由 `commerce_migrator` 管理；通过默认权限让后续表自动授予 `commerce_app` 必需的 `SELECT/INSERT/UPDATE/DELETE` 和序列使用权。密码只进入 Git 已忽略的本地环境文件或受控密钥存储。

## 10. 安全配置

- `listen_addresses = 'localhost'`。官方说明该参数控制服务器监听地址，默认是本机回环：[Connection settings](https://www.postgresql.org/docs/current/runtime-config-connection.html)。
- `pg_hba.conf` 只允许本机 IPv4/IPv6 回环，并使用 `scram-sha-256`；规则按顺序匹配，应保持范围最小：[Client authentication](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html)。
- `password_encryption = 'scram-sha-256'`。
- 不开放 5432 防火墙入站，不使用公网地址作为数据库连接地址。
- Commerce Ops 使用 `commerce_app`，不使用 `postgres`。
- `DATABASE_URL` 只进入被 Git 忽略的本地配置，并且在 F2 Provider 完成前不修改正式值。
- 日志、doctor、错误响应和迁移报告不得打印密码或完整连接串。
- 数据库统一 UTC 存储；国家/店铺时区作为业务字段保留。

## 11. 分阶段迁移路线

| 阶段 | 正式业务影响 | 用户操作 | 可回滚 | 完成标准与失败停止条件 |
|---|---|---|---|---|
| F1 安装与空环境 | 无 | 批准 UAC、设置管理员密码 | 可卸载未承载业务的空服务 | 服务仅回环、工具可用、空测试库/最小角色正确；端口或权限异常立即停止 |
| F2 Provider 与 DDL | 无，SQLite 仍为正式 Provider | 无 | 删除测试库/回退代码提交 | 两种 Provider 契约测试通过；DDL、权限或事务语义不一致停止 |
| F3 SQLite 副本导入演练 | 无，只使用一致性副本 | 确认演练窗口 | 重建测试库 | 全表导入、约束和日志通过；任何行转换失败停止 |
| F4 SQLite/PostgreSQL 对账 | 无 | 审阅对账报告 | 保持 SQLite 不变 | 行数、主键摘要、分组、空值、FK、JSON、文件元数据一致；差异不为零停止 |
| F5 正式数据迁移 | 短暂停止写入和调度 | 确认维护窗口 | 正式 SQLite 仍保留 | 最终副本导入并对账一致；活动任务或文件变更时停止 |

F0 没有执行上述任何阶段。

## 12. 对账与切换准则

每张表至少比较：行数、主键集合摘要、唯一键冲突、状态/类型分组、关键列空值数、最早/最晚时间、JSON 有效性和外键孤儿数。文件相关表额外比较文件 ID、相对路径、大小和 SHA-256；文件本身继续存储在文件系统，不导入 PostgreSQL。

双写期间 SQLite 仍是权威源。任何 PostgreSQL 写入失败必须可观测并进入重试/补偿记录，不能静默忽略。切换时只能运行一个调度器，先停止写入、排空运行中任务、完成最终增量和对账，再切读取 Provider。

## 13. 回滚方案

### PostgreSQL 服务无法启动

保持 Commerce Ops 使用 SQLite，不修改正式 `DATABASE_URL`；检查 Windows Event Viewer、服务账号、数据目录权限和 5432 冲突。F1 空环境没有业务数据，可以修复安装或卸载后重装，不影响正式 SQLite。

### 演练导入失败

停止 F3/F4，保留失败日志但不含敏感值，删除并重建 `commerce_ops_migration_test` 后重试。正式 SQLite 和文件目录保持不变。

### 双写或读取切换失败

停止调度和写入，将 Provider 配置切回 SQLite，确认只有一个调度器启动，执行 SQLite integrity、业务计数和文件 manifest 核验，再恢复服务。切换后的 PostgreSQL 数据保留为取证副本，不反向覆盖 SQLite，除非另有经过验证的增量恢复脚本。

### PostgreSQL 备份与迁云

使用当前或更高版本客户端执行 `pg_dump -Fc`，上传 dump 和文件存储备份到独立位置，在云 PostgreSQL 临时库用 `pg_restore` 演练并对账；确认后仅修改后端数据库连接。Web 前端和业务接口不应依赖数据库物理地址。

## 17. F1 精确实施建议

F1 应单独执行并在完成后停止：

1. 复核主/广告 Git 干净、C/D 备份可读、SQLite integrity、无活动任务、5432 空闲。
2. 用户从官方入口下载 PostgreSQL 18 当前 x64 小版本并手工运行安装器。
3. 按第 8 节参数安装，服务只监听本机，不创建防火墙入站规则。
4. Codex 只读验证版本、服务、端口、编码、时区、认证方式和工具链。
5. 经用户确认后创建空的 `commerce_ops_migration_test`、规划角色和 `app` schema；`commerce_ops` 可创建为空库，但不得导入或接管业务。
6. 运行连接/权限负面测试，验证 `commerce_app` 不能建库、建角色或执行 DDL。
7. 记录安装版本、服务名和配置备份，不安装 Node `pg`，不修改正式 `DATABASE_URL`，不导入 SQLite。

F1 完成标准：PostgreSQL Windows 服务自动启动、仅回环监听 5432、UTF-8/UTC/SCRAM 配置正确、测试库和最小角色可用、正式 SQLite 与四个业务模块完全不受影响。
