# COM-GROWTH-RADAR-V2.2-INT-0.1 门禁报告

## 1. 门禁结论

本节点只执行指标合同、马帮来源解析边界和共享工作树归属审计，没有修改业务代码、迁移、数据库或前端。

当前门禁结论：

| 门禁 | 结果 | 说明 |
| --- | --- | --- |
| `GRV2-METRICS-1.2.0` 正式合同 | `WAITING_CONFIRMATION` | 可以作为 1.1.0 的版本化后继合同，但仍有未确认阈值和一项可售天数口径缺口 |
| 马帮数据解析边界 | `PARTIAL_PASS` | 已区分纯解析修正和业务规则变化；纯解析部分可做最小修正，业务规则部分必须随 1.2.0 批准 |
| 共享文件修改隔离 | `PLAN_READY` | 已形成安全提交边界，但当前混合工作树尚未实际拆分 |
| 是否可以开始业务开发 | `NO` | 按本节点要求，发现业务规则变化后停止等待人工确认 |

总判断：

> `GRV2-METRICS-1.2.0` 的方向正确，能够替代 1.1.0 成为新的正式计算合同，但不能覆盖或重新解释历史 1.1.0 结果。关闭本报告第 2.4 节的业务口径问题后，才能批准解析修正和 V2.2 主线实现。

## 2. 指标合同升级确认

### 2.1 是否可以替代 1.1.0

可以，但必须采用“后继版本”而不是原地替换：

```text
历史分析运行
→ 继续引用 GRV2-METRICS-1.1.0

新分析运行
→ 只在批准后引用 GRV2-METRICS-1.2.0
```

不得：

- 修改历史 1.1.0 参数；
- 用 1.2.0 重新解释旧 published 结果；
- 静默改变旧运营任务证据；
- 在 1.2.0 批准前修改正式规则集。

### 2.2 1.2.0 的必要性

权威样本和已冻结的 `GRV2-MABANG-SOURCE-1.0.0` 已证明 1.1.0 存在以下过期假设：

| 范围 | 1.1.0 | 1.2.0 候选 |
| --- | --- | --- |
| 有效订单 | 仅 `已发货` | `已发货`、`待处理`、`配货中`、`已完成` |
| 销量日期 | `paid_at`，来源含义未充分说明 | 明确对应马帮 `付款时间` |
| 高表现货盘 | 来源 28 天销量类目 P80 | 国家、类目内按货盘预测日销量 P80 |
| 多仓预测日销量 | 不累加或仅作旁证 | 同国家唯一仓库求和 |
| 当前可售天数 | 系统重算 | 直接使用马帮仓库级结果 |
| 活跃度 | Commerce Ops 自有规则 | 第一版保留马帮 `爆款/旺款/平款/滞销款` |
| 新品 | 产品中心生命周期 | 第一版使用来源 `是否新款=是` |
| 店长 | 依赖内部配置 | 来源店长作为默认建议，人工覆盖优先 |
| 趋势 | 未完整冻结 | 当前 7 天与前 7 天比较 |

因此，继续使用 1.1.0 会直接违反已确认的来源事实。

### 2.4 尚未解决的业务口径

以下项目属于业务规则，不是解析修正。按任务要求，检测到这些项目后必须停止等待人工确认。

#### A. 10 项候选默认值尚未整体批准

候选合同第 12 节仍明确标记为“正式批准前需要人工确认”，包括：

- 趋势变化率 `10%`；
- 前期最小销量 `5`；
- 最小绝对变化 `3`；
- 高表现阈值 `P80`；
- 类目最小样本 `30`；
- 低承接阈值 `10%`；
- 普通类目缺口覆盖率 `< 50%`；
- 严重类目缺口覆盖率 `< 25%` 且缺口至少 10 个 SKU；
- P0 严重下降 `-50%` 且绝对减少至少 20；
- 每位店长首页最多 10 项任务。

#### B. 候选合同中还有未进入确认清单的阈值

以下常量已经出现在规则正文，但没有全部出现在第 12 节的人工确认清单：

- `new_sales_min_quantity = 5`；
- `SALES_STOPPED` 的前 7 天销量至少 20；
- P1 下滑的 `-20%`、绝对减少 5、前 7 天至少 10；
- 类目缺口的 `eligible_high_sku_count >= 10`；
- 重点 SKU 可售天数 `1-7` 和 `8-14` 的任务分级。

这些值应加入正式确认清单，不能仅因为写在文档正文就视为批准。

#### C. 国家级可售天数仍缺少单一判定方式

来源合同明确规定：

```text
当前可售天数 = 仓库级来源事实
```

并禁止跨仓求和或平均。

但是 1.2.0 的 P1/P2 任务会根据 `1-7`、`8-14` 天进行分级，尚未明确同一国家、同一 SKU 有多个仓库时如何命中：

- 任一仓库命中；
- 最小值命中；
- 仅实际履约仓库命中；
- 每个仓库分别产生风险，再在页面聚合。

推荐第一版采用：

> 每个仓库分别计算供给风险，国家级页面只聚合风险数量和展示最危险仓库，不生成一个伪造的国家可售天数。

该推荐仍需人工确认。

#### D. “市场验证”内部命名需要最后确认

合同已正确禁止把 `货盘预测日销量` 称为市场真实销量或市场份额，但内部规则仍使用：

```text
MARKET_VERIFIED_HIGH
MARKET_VERIFIED_MID
MARKET_LOW
```

这容易让 API、日志或后续 AI 错误解释为外部市场数据。

建议在正式合同中改为更准确的稳定规则码，例如：

```text
ASSORTMENT_VERIFIED_HIGH
ASSORTMENT_VERIFIED_MID
ASSORTMENT_LOW
```

页面继续使用“高表现货盘”或“已验证货盘”，不使用“市场份额”。

## 4. 解析边界分类

### 4.1 A 类：数据解析修正

以下修正只负责无损读取来源，不改变机会、风险和销量规则。

#### 订单

1. 将 `店长` 和 `国家` 加入安全允许字段。
2. 仅对订单头字段执行同订单范围内的向下继承：
   - 订单编号；
   - 店铺名；
   - 平台；
   - 店长；
   - 订单状态；
   - 仓库；
   - 国家；
   - 付款时间。
3. SKU、商品数量、商品中文名称等商品字段永不继承。
4. 文件开头或订单边界外的孤立商品行 fail-closed。
5. 保留来源原始订单状态，不在 parser 内决定 1.2.0 是否计入销量。
6. 保存订单国家和来源店长作为来源证据，不覆盖已确认的内部配置。

#### 库存

1. 继续按 `SKU + 仓库` 保留每条事实。
2. 解析并保留：
   - `销量(7/28/42)`；
   - `预测日销量(个)`；
   - `当前可售天数`；
   - `活跃度`；
   - `是否新款`；
   - 一级、二级目录；
   - 商品状态；
   - 可用库存和在途量。
3. 空活跃度保持 `NULL/unavailable`，不转为平款或滞销。
4. 正常中文仓库原样保存，国家由独立配置决定。

#### 最小修改范围

在不创建 migration 的前提下，纯解析修正应限制为：

- `scripts/growth-radar-parser.py`
- parser/preview 专项测试和真实脱敏 fixture
- 必要的预览 DTO 字段
- 已有原始行 JSON 和证据 JSON 的字段保留

现有 `growth_inventory_snapshots` 已有 `days_of_supply` 和状态字段，可以保存来源可售天数，不需要为该字段新增迁移。

`店长`、订单来源国家、活跃度和新品标记当前没有完整的结构化事实列。无 migration 阶段可先无损保留在原始行和标准化证据中；是否提升为可查询列，应随修订后的 019 候选结构单独评审，不能偷偷修改 013/014。

### 4.2 B 类：业务规则变化

以下内容不是 parser 修复，必须由正式指标合同控制：

1. 四种订单状态是否计入我方销量。
2. 付款时间如何切分当前 7 天、前 7 天和 28 天窗口。
3. 同国家唯一仓库预测日销量的求和。
4. 国家、类目内 P80 高表现货盘判定。
5. 马帮活跃度是否参与任务，仅展示还是作为证据。
6. `是否新款=是` 是否产生新品候选。
7. 店长来源值与人工覆盖的优先级。
8. 仓库级当前可售天数如何产生国家级任务。
9. P0/P1/P2/P3 的全部阈值和排序。

这些规则应在 V2.2 engine 和 versioned rule set 中实现，不应写死进 parser 或改变 A2 的历史 `effective_status` 含义。

### 4.3 当前 parser 的具体缺口

当前实现证据：

- `ORDER_ALLOWED_HEADERS` 不包含 `店长` 和 `国家`。
- parser 对每一行独立标准化，没有订单头续行继承。
- 每一商品行都要求订单编号、平台和店铺，因此 24,373 条合法续行存在被拒绝风险。
- `已发货` 被映射为 `valid`；`配货中`、`待处理` 和 `待审核` 均映射为 `pending`；`已完成` 为 `unconfirmed`。
- 库存解析已读取 7/28/42 和预测日销量。
- `daysOfSupply` 被固定为 `None/unavailable`。
- 活跃度和是否新款未进入标准化结果。

因此不能在当前 parser 之上直接发布 1.2.0 正式分析。
