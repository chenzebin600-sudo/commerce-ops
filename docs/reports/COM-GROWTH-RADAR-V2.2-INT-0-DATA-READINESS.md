## 1. 审计依据

业务负责人确认未来马帮数据模块将持续导出以下两类数据。本报告以人工导出的真实文件为
字段和容量基线：

- 订单：用户提供的样例工作簿 `订单1.xlsx`
- 库存：用户提供的样例工作簿 `库存1.xlsx`

数据库现状仍作为“当前导入完成度”的证据，但不再用旧数据库缺字段来否定 Excel 已明确
提供的来源能力。

## 2. 结论

Growth Radar V2.2 的核心来源字段已经足够，不需要重建订单或库存事实底座。

与上一次仅基于正式数据库的审计相比，本次真实文件确认：

1. 订单源实际包含 131 家店铺和 21 名店长，每家店铺在样本中只有一个当前负责人。
2. 订单源包含显式国家、平台、店长和付款时间。
3. 订单付款时间覆盖 2026-07-12 至 2026-07-26，共 15 个连续日期，已经可以计算
   当前 7 天与前 7 天趋势。
4. 库存源包含 24 个正常仓库，不存在数据库中出现的 3 个乱码仓库别名；乱码属于旧导入
   编码缺陷。
5. 库存源直接提供 SKU + 仓库粒度的 7/28/42 天货盘销量、预测日销量、当前可售天数、
   活跃度和新品标记。
6. 多仓预测值不同不是数据冲突。业务已确认它们属于不同仓库事实，应在国家内按唯一仓库
   求和。

正式启用仍需完成四项准备：

1. 导入器按真实 Excel 结构完整落库。
2. 用户在前端确认 24 个仓库的国家映射。
3. 店铺来源负责人入库并支持人工覆盖。
4. 批准 `GRV2-METRICS-1.2.0`，显式替代旧指标合同中的冲突规则。

### 3.2 店铺负责人

样本中的 131 家店铺：

- 每家店铺只对应一个店长；
- 每家店铺只对应一个国家；
- 每家店铺只对应一个平台；
- 没有发现同店铺多负责人冲突。

因此，来源 `店长` 可以作为当前实际负责人的默认值。配置流程调整为：

1. 导入来源店铺、店长、国家和平台。
2. 生成店铺身份与负责人的预览。
3. 用户确认或人工修改。
4. 人工修改后保存内部负责人和来源负责人两个值。
5. 后续来源变化只提示差异，不覆盖人工确认。

不再建议把全部店铺默认归属一个店长，也不再把 107 家旧数据库店铺视为完整来源范围。
正式导入后应以来源 131 家店铺重新做身份匹配和增量补齐。

## 4. 国家映射准备

真实库存文件中有 24 个正常仓库，不包含旧数据库的 3 个乱码别名。

处理方案：

1. 前端读取最新来源仓库清单。
2. 系统可根据仓库名提供国家候选。
3. 用户逐项或批量确认受控国家代码。
4. 配置版本化保存到数据库。
5. 只有 24/24 仓库得到确认或明确排除后，国家级分析才能发布。
6. 正式分析运行绑定具体国家映射版本。

旧数据库中 3 个乱码仓库应进入导入编码修复与数据清理方案，不应要求用户把它们当作
独立仓库配置，也不应把真实来源行排除。

订单已有显式 `国家`，应作为订单国家首选事实。订单国家与仓库配置不一致时生成质量
告警。本次样本发现：

- 15 个订单头的国家与仓库名称前缀不一致；
- 10 个订单使用特殊或无法解析仓库。

这些记录应进入质量队列，不阻断其他正常订单导入。

## 5. 数据趋势准备

### 5.1 可以立即使用

#### 货盘来源窗口

库存文件已经提供：

- SKU + 仓库近 7 天货盘销量；
- SKU + 仓库近 28 天货盘销量；
- SKU + 仓库近 42 天货盘销量；
- 来源预测日销量；
- 当前可售天数；
- 马帮活跃度；
- 来源新品标记。

这些指标不需要等待系统自行积累 28 或 42 天快照，但必须明确标注为货盘来源数据，
不能称为平台市场总销量。

#### 我方 7 天趋势

订单付款时间连续覆盖 15 天，已经满足：

```text
当前 7 天
vs
前 7 天
```

可立即计算：

- 店铺 7 天增长、下降和稳定；
- SKU 7 天增长和衰退；
- 店铺趋势异常；
- 店长今日趋势任务候选。

计算时使用四个已确认有效状态，不能继续只筛“已发货”。

### 5.2 仍需等待或持续积累

#### 我方 28 天窗口

当前订单文件只有 15 个连续日期，因此暂不能正式发布：

- 我方近 28 天销量；
- 近 28 天销售覆盖率；
- 近 28 天货盘承接率；
- 以“我方 28 天销量为 0”为必要证据的蓝海/跨国候选；
- 需要 28 天稳定性的重点跟进款。

解决方式：

- 后续每日增量连续积累到 28 天；或
- 马帮订单导出改为稳定的滚动 42 天范围。

缺失日期不能补零。只有成功同步且明确无订单的日期才可以记录为真实 0。

#### 我方 42 天窗口

货盘来源 42 天窗口已可使用；我方 42 天趋势仍需连续订单历史。两者必须分开命名和展示。

#### 库存历史趋势

单次库存文件可以提供当前货盘和来源窗口，但不能证明库存随时间变化。库存趋势需要每天
保存成功快照后逐步形成。

### 6.2 满足我方 28 天连续历史后上线

- 我方近 28 天货盘承接率；

### 6.3 暂不启用

- 没有国家映射的仓库数据；
- 没有证据链的推荐。

## 7. 合同差异

真实来源确认与 `GRV2-METRICS-1.1.0` 存在以下正式差异：

| 范围 | `1.1.0` | 来源确认 |
|---|---|---|
| 我方有效订单 | 仅已发货 | 已发货、待处理、配货中、已完成 |
| 订单日期 | 原合同未以真实文件冻结 | 付款时间 |
| 多仓预测日销量 | 不累加、不同即冲突 | 国家内按唯一仓库求和 |
| 当前可售天数 | 系统用库存和 28 天销量重算 | 直接使用马帮结果 |
| 活跃度 | 系统规则为主 | 第一版使用马帮分类 |
| 新品 | 依赖产品中心生命周期 | `是否新款=是` |
| 店长 | 旧库全部待配置 | 来源店长为当前负责人，允许人工覆盖 |

因此：

1. `GRV2-METRICS-1.1.0` 保留历史，不直接改写。
2. 必须创建并批准后继合同 `GRV2-METRICS-1.2.0`。
3. `1.2.0` 批准前不启动正式分析，不发布运营任务。
4. 本节点不新增 migration；迁移是否需要变化由后续只读实现审计决定。
