# Commerce Ops 控价变更模块

## 目标

让 Commerce Ops 在不回写 `AI_Project_A` 的前提下，只接收已审批通过（`CA`）的控价批次，建立可追溯基线，并将最新控价与本系统上一次有效控价逐项比较。每条变化必须形成可复制文本、Foundation 人工任务与 Audit 记录。

标准文本：

> 国家：TW；类目：家具用品；SKU：T3AA2041455；商品中文名：折叠收纳架；平台：Shopee；店铺类型：Mall 店；价格类型：活动价；从原价 199.00 变更到现价 189.00，下调 10.00（5.03%）。

## 架构归属

- 源数据适配器：`lib/price-control/mysql-price-control-source.mjs`，使用独立 MySQL 连接池，每次读取显式开启只读一致性快照并回滚释放。
- 领域层：`PriceControlService` + `PriceControlRepository`，接入统一 `openCommerceDataAccess`，不创建第二套数据库运行时。
- 任务：每个“申请批次 + 国家”的变化创建一个 `product / price_control_change_review` Foundation 人工任务。
- 审计：手动同步请求、同步成功和同步失败进入现有 Operation Audit。
- 调度：复用现有 `scheduler.mjs` 进程和单例设置，默认每 60 分钟在整点检查控价；即使一次执行稍有延迟，下一次仍重新对齐整点，不会逐次漂移，也不创建第二套调度服务。
- 通知：复用现有加密的 `dingtalk_robot_configs` 注册表和钉钉发送适配器。只有检测到新变化或同步失败且规则允许时才发送；无变化不打扰。消息必须显示完整的平台分布，并在篇幅受限时跨 Lazada、Shopee、TikTok Shop 轮询抽样，不能直接截取数组头部造成单平台偏差。
- 前端：Vue 主工作区 `/price-control`，使用现有认证、Element Plus、导航和响应式设计系统。

## 数据口径

1. `apply_no` 是申请批次；源表每行是国家下的一个 SKU 申请明细，不是原始文件附件。
2. 仅 `curr_approve_status='CA'` 生效。`BA` 等审核中批次不会进入基线或触发提醒。
3. 15 个宽价格字段标准化为：国家 + SKU + 平台 + 店铺类型 + 价格类型。
4. Lazada、Shopee 分标准店/Mall 店；TikTok Shop 当前只有标准店字段。
5. 日常、活动、大促分别映射为 `REGULAR`、`CAMPAIGN`、`MEGA_CAMPAIGN`。
6. 金额按整数分比较，不使用二进制浮点判断。
7. 商品中文名只从同一源库 `product_package` 的 `country + stock_sku` 补充；匹配不到时明确显示“未匹配中文名”，不推测。
8. 首次必须执行 `baseline`。基线只保存当前价，不把既有价格误报为新增；以后执行 `incremental` 才生成变化。
9. 每次只读取每个“国家 + 类目”的最新 `CA` 批次；同一价格身份如果在多个最新批次中重叠，只保留审批业务时间最新的一项。增量水位使用审批/提交/创建业务时间和已处理批次指纹，不读取最近若干历史批次凑窗口，不使用全为空的 `apply_update_time`，也不依赖 Navicat 无排序的物理行顺序。
10. 源价格列 `NULL` 表示“本批次未维护该价格维度”，系统沿用上一次非空控价，不更新当前价、不生成变化。
11. 只有旧值和新值均为数值且不同才生成上涨/下调。没有上一条有效价格的 SKU/价格维度只进入当前价格基线，不生成“新增”变化、前端话术或钉钉提醒。
12. 移除必须由源库提供明确删除标识。当前源表没有此标识，因此 `NULL` 永远不会生成移除。

## 当前人工处理与马帮调价工作流

当前阶段使用可审计的人工闭环：

1. 控价模块默认进入正式的 SKU 控价变更明细，按筛选条件展示国家、类目、SKU、中文名、平台/店铺、原价、现价和方向；支持勾选多条后“复制选中”，或直接“复制本页”，每条变化文本以换行分隔。“当前控价”保留为辅助查看标签。
2. 变更明细按 `sync_run_id` 形成“变更轮次”。页面默认选中最近一次有有效变化的轮次，显示最近变更时间、源库控价更新时间、相关 SKU 数、本轮变更数及已调整/未调整数量；列表即为该轮相关 SKU 明细。“本轮变化 / 上轮变化”分别快捷定位最近一次和再前一次产生有效变化的同步轮次，无变化的定时检查不占用轮次位置，并保留历史轮次下拉供追溯。
3. “复制本轮全部信息”一次读取该轮所有有效变更，文本带轮次头、时间、SKU 数、每条完整变化、处理状态和备注；单轮安全上限为 250,000 条，避免无界内存占用。
4. 每条变化可以打开处理对话框，标记“未调整/已调整”并填写备注。保存有明确加载与成功/失败反馈；移动端使用卡片状态和不小于 44px 的处理按钮。
5. 保留复制到马帮后人工处理的原有路径；同时新增候选调价链路，但不会因为控价变化自动修改马帮或平台价格。
   控价差异检测只依赖只读源库和本地上一有效价格，与马帮刊登预览、马帮写价或未来官方平台 API 完全解耦；这些接口只消费已经形成的变化，不参与决定某个 SKU 是否发生控价变化。
6. 用户只能从“最近一次有有效变化的轮次”选择未调整记录，并为每条“国家 + SKU + 平台 + 价格类型”显式选择同平台、同国家的一个或多个有效店铺。系统不自动猜店铺；同 SKU 分布在多个国家时也不会跨国家匹配。
7. `REGULAR` 映射到马帮 `price`，`CAMPAIGN` 映射到 `special_price`。`MEGA_CAMPAIGN` 和 TikTok Shop 当前没有可证明安全的执行语义，因此直接阻断。
8. 系统先把已选控价变化与店铺组装成从 1 开始编号的自然语言，再交给现有 AI 指令解析；服务器逐条校验 AI 返回的平台、国家、店铺、SKU、动作、字段、目标价和 `need_confirm`，任何语义漂移都会在访问价格预览前阻断。多条指令的马帮差异必须带有效且有界的源指令序号，不能把一个国家的结果回挂到另一个国家。
9. 校验通过后调用马帮刊登的实时批量预览，展示马帮实际匹配到的商品/变体、当前值、目标值和阻断原因。共同执行账户必须明确具备本次所需的 `price` / `special_price` 写入能力；只接受控价 SKU 精确命中，或 `源 SKU + S1…S9` 的有界虚拟 SKU 命中。虚拟命中必须把控价 SKU 与实际 SKU 并列显示并警示；无剩余有效期、旧值不是可判定价格、或重复指向同一商品变体字段的预览都会失败关闭。预览令牌只保存在服务器，前端只得到不可伪造的预览指纹与实际差异项。
10. 实际差异默认全部不勾选。执行必须满足五个条件：预览未过期、指纹一致、用户勾选具体实际差异、输入完整确认语“确认同步到店铺”、对所选 `UNKNOWN` 店铺类型作明确承认。确认前重新校验最新有效轮次、来源变化仍未调整、店铺及执行账户/字段能力仍有效且范围未变；数据库原子状态抢占再次关闭新轮次竞态并禁止重复提交。马帮共享会话的账户连接、预览、提交和回读按账户操作串行化，避免并发切换账户导致越界。网络结果不确定、马帮受理响应缺少任务编号，或平台已受理但本地执行状态落库失败时，进入 `EXECUTION_UNKNOWN`，不得自动重试写价。
11. 计划状态为 `PREVIEW_READY → CONFIRMING → EXECUTING → SUCCEEDED / PARTIAL / FAILED`，另含 `EXECUTION_UNKNOWN / EXPIRED / CANCELLED`。只有平台逐商品明确返回成功才算成功；终态缺少商品级结果时保持 `EXECUTION_UNKNOWN`。某条来源变化只有在所有计划差异均已选择且成功、且所有最初分配店铺都有真实差异成功证据时，才标记为 `ADJUSTED` 并写入 Audit。
12. 当前执行器为 `MABANG_LISTING`。领域服务只依赖统一调价适配器边界，后续可接 Lazada/Shopee 官方平台 API，但仍必须复用相同的真实差异预览、人工确认、幂等状态和回读审计约束。

源 MySQL 只允许硬编码的 `SELECT` 查询。连接密码只从环境变量读取，不进入迁移、业务表、日志、前端或文档。
