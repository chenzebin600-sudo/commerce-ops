# ZNWX OperationPlan 基础设计

## 目的

`OperationPlan` 是一次高风险写操作在真正执行前生成的不可变计划。它把“准备做什么、基于哪份数据、谁批准、实际执行到了哪里”固化为可校验记录，避免预览内容与最终提交内容发生静默漂移。

当前实现只提供通用基础能力，尚未替换自动发货现有执行链，也不会因为迁移或服务启动而自动提交业务写操作。

## 从 RE 借鉴的边界

| 能力 | ZNWX 当前决定 |
| --- | --- |
| 统一写操作状态机 | 借鉴，落地 `PREVIEWED → APPROVED → IN_FLIGHT → SUCCEEDED/FAILED/UNKNOWN` |
| 输入与计划内容哈希 | 借鉴，使用规范 JSON 与 SHA-256 固化计划、范围、快照、策略和条目 |
| UNKNOWN 语义 | 借鉴，超时或结果不确定时禁止直接重试，只允许基于官方读回证据对账 |
| 人工/系统批准 | 借鉴，分别记录批准方式与精确批准文本哈希 |
| 敏感数据隔离 | 借鉴，计划内容拒绝密码、令牌、Cookie、Authorization 等字段 |
| RE 的 JSON 数据库 | 不迁移，继续使用 ZNWX 现有仓储与迁移体系 |
| RE 的巨型适配器与 Next.js 前端 | 不迁移，保持 ZNWX Vue 主入口和模块化服务边界 |

## 数据与状态契约

- 计划内容创建后不可变；仓储只允许更新状态、结果、批准信息和版本号。
- 每次状态变化写入独立事件记录，并使用乐观版本避免并发覆盖。
- 执行前重新计算计划哈希，并校验范围、数据快照、策略和操作条目哈希。
- 任一输入漂移都进入 `BLOCKED`，不得继续执行旧计划。
- 计划超过有效期进入 `EXPIRED`；已取消计划进入 `CANCELLED`。
- `UNKNOWN` 表示写请求可能已生效但没有可信结果，禁止把它当普通失败自动重试。
- `UNKNOWN` 只能凭目标系统的官方读回证据转为 `SUCCEEDED`、`FAILED` 或 `BLOCKED`。

## 自动发货迁移顺序

1. **旁路建模**：从现有扫描预览生成 OperationPlan，但不改变提交逻辑。
2. **影子核对**：对比现有候选订单与计划哈希、库存快照、仓库和渠道策略，只记录差异。
3. **执行前门禁**：在真实提交前要求计划未过期、输入未漂移、店铺在静态授权白名单内。
4. **结果对账**：把马帮官方订单/运单读回作为成功依据；网络超时进入 `UNKNOWN`，不直接重试。
5. **小范围切换**：仅对白名单店铺启用新链路，保留现有并发、批次上限和人工处理降级。
6. **全量切换**：持续观察自然批次后再逐店扩展；任何安全指标异常都回到只检查模式。

今天只完成第 1 步所需的通用底座和现有履约配置安全加固，未把生产自动发货切到新协议。

## 适配器进入执行前的最低条件

- 能返回目标系统身份、账号和店铺范围，且与计划范围完全一致。
- 能声明快照采集时间和新鲜度；超过业务允许窗口时拒绝执行。
- 能做只读预检，并将库存、仓库、渠道、订单状态等关键输入纳入哈希。
- 能提供幂等键或官方结果读回路径；两者都没有时不得自动重试不确定写操作。
- 能区分业务拒绝、确定失败和未知结果，不能把网络异常统一归类为失败。

## 上线注意事项

- 数据库迁移为 `023_foundation_operation_plans.sql`，在生产进程安全重启或明确执行迁移前不会进入当前运行库。
- 当前 3112 为真实自动发货服务；应用新代码前必须确认 `scanning=false` 且 `activeBatch=null`。
- 手机端验收本轮延期；桌面端只读验收不包含扫描、同步、登录或保存操作。
