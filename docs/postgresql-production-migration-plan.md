# Commerce Ops PostgreSQL 正式迁移执行方案（F5）

日期：2026-07-20
状态：PLAN COMPLETE / NOT EXECUTED
当前生产数据库：SQLite
未来目标数据库：PostgreSQL `commerce_ops.app`

> 本文仅定义未来正式迁移的执行、校验、观察和回滚流程。F5 不执行数据迁移，不修改 `DATABASE_PROVIDER`，不切换生产读取，不删除 SQLite，也不修改业务模块。

## 执行前置结论

F0-F4 已经证明：

- PostgreSQL 本机环境和最小权限角色可用。
- 15 张 SQLite 表可完整转换为 PostgreSQL 原生类型、索引和约束。
- 636 行演练数据在 `commerce_ops_migration_test.app` 中实现全表哈希一致。
- 同一套兼容 Repository 合约可在 SQLite 和 PostgreSQL 上执行 CRUD、事务和约束错误处理。

但当前生产应用仍由 `lib/data/data-access.mjs` 打开同步 SQLite Repository。F4 新增的是兼容验证层，不是生产运行路径切换。因此正式迁移还有一个不可跳过的 Go/No-Go 前置条件：

1. 所有生产持久化服务接入异步、Provider 无关的 Repository。
2. 使用 `commerce_app` 角色在独立 staging 数据库完成完整接口和业务回归。
3. 调度器、文件元数据、审计和启动恢复流程通过 PostgreSQL staging 测试。
4. 回滚增量脚本完成演练。

任何一项未完成，正式迁移不得开始。

## 1.3 当前增长趋势

当前增长主要来自审计事件、任务步骤、缓存和文件生命周期记录，属于低到中速增长。进入 50 家店铺运营后，增长重心会转向业务事实表：

- 订单与订单明细：持续追加，必须有平台、店铺、日期和订单号唯一键。
- SKU、SPU、平台链接：主数据增长较慢，但关联密度高。
- 库存快照：若按“店铺 × SKU × 日期”全量保存，增长非常快。
- 广告指标：按“日期 × 店铺 × 计划 × 商品/关键词”增长。
- AI 分析记录：行数未必最大，但输入摘要、输出、模型和引用数据可能占用较多空间。
- 操作日志与同步日志：自动任务越多，增长越稳定且不可忽略。
- 产品包与素材：结构化元数据进入数据库，图片、Excel、视频本体仍进入文件或对象存储。

# 第二部分 为什么未来需要 PostgreSQL

## 2.1 SQLite 当前优势

- 单文件部署，开发和备份简单。
- 本机单用户工具维护成本低。
- 当前 636 行数据和低并发任务完全能够承载。
- 无独立数据库服务账号和网络配置负担。
- 出现问题时复制一致性备份即可恢复。

## 2.2 SQLite 的后续限制

- 同一时刻只能有有限写并发，采集、调度、审计和多人操作容易争夺写锁。
- 多进程、多用户和远程服务下，单文件锁与共享路径管理更复杂。
- 订单、库存、广告和链接指标达到百万至千万行后，长期分析与维护空间受到限制。
- 数据库权限不能像服务端数据库一样按角色隔离。
- 云端部署、故障转移、集中备份和监控能力有限。
- AI 分析、定时采集和看板查询并发时，更容易互相影响。

## 2.3 PostgreSQL 的价值

- 支持多连接和更强的并发读写能力。
- 可通过 `commerce_migrator` 与 `commerce_app` 分离 DDL 和业务 DML 权限。
- 原生支持 `jsonb`、UUID、`timestamptz`、复杂聚合、窗口函数和丰富索引。
- 更适合多人访问、后台任务、分析查询和长期历史数据。
- 可从本机 PostgreSQL 平滑迁往服务器自建 PostgreSQL 或托管云数据库。
- 可接入集中日志、备份、连接池、慢查询、监控和时间点恢复能力。

迁移原因不是当前 SQLite 已无法使用，而是未来业务数据模型、并发和团队访问方式会发生变化。

# 第三部分 正式迁移流程设计

## 总体原则

- 迁移必须在审批后的低峰维护窗口执行。
- SQLite 在整个迁移和观察期内保留，不删除、不覆盖。
- 正式切换前只有一个权威写入源，禁止临时双写。
- 主服务和调度器必须同时停写，不能只关闭浏览器页面。
- 数据迁移成功不等于业务切换成功，必须经过应用角色和完整业务验收。
- 任一停止条件触发后，保持 SQLite 生产，不带病切换。

## 阶段 1：迁移准备

### 1.1 发布和审批

- 固定迁移候选 Git commit，创建迁移标签并记录负责人。
- 明确维护窗口、预计停机时间、通知对象、执行人和回滚负责人。
- 冻结迁移相关代码、Schema 和环境配置变更。
- 确认 staging 已使用 `commerce_app` 通过完整回归，而不是只使用迁移角色测试。
- 确认回滚增量脚本已在演练库完成至少一次恢复演练。

### 1.2 SQLite 双介质备份

停止写入后执行：

1. WAL checkpoint。
2. 使用 SQLite 官方 Backup API 或 `VACUUM INTO` 生成一致性副本。
3. 保留原始 SQLite、WAL、SHM 文件快照。
4. 对一致性副本执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`。
5. 生成数据库、配置清单和正式文件的 SHA-256 manifest。
6. 将完整备份保存到两个独立存储介质，不得只保存在系统盘。

### 1.3 PostgreSQL 备份和健康检查

- `pg_isready` 正常。
- PostgreSQL 服务无启动错误，磁盘空间满足数据库、临时文件和至少两份备份需求。
- 正式库当前状态已记录；即使是空库，也先保存 globals 和数据库结构基线。
- `commerce_migrator` 可管理 `app` Schema，但不是超级管理员、不能建库或建角色。
- `commerce_app` 只能连接、使用 `app` Schema 和执行必要 DML，不能执行 DDL。
- 默认权限确保迁移角色未来创建的表和序列自动授权应用角色。
- 数据库时区为 UTC，编码为 UTF-8。
- 5432 仅位于受控本机或私有网络，不向公网开放。

### 1.4 应用、磁盘和文件检查

- `npm test`、`npm run build`、`npm run doctor` 全部通过。
- `npm run postgres:f1:protect -- verify` 为 `UNCHANGED`。
- `npm run postgres:f4:check` 通过。
- 正式文件总数、大小和 SHA-256 与数据库文件元数据一致。
- 导出根目录、广告文件目录、临时目录和备份目录空间充足。
- 环境变量文件已备份且未进入 Git，报告中不打印密码或连接串。

### 阶段 1 Go/No-Go

以下任一情况必须停止：

- SQLite integrity 不是 `ok` 或存在外键异常。
- 文件 manifest 不一致。
- PostgreSQL 权限边界不正确。
- staging 业务回归失败。
- 回滚增量方案未演练。
- 可用备份只有一份或无法恢复验证。

## 阶段 2：停止写入

按顺序执行：

1. 在系统界面进入维护状态，阻止新写请求。
2. 停止调度器，禁止创建新的 scheduled run。
3. 等待运行中的马帮任务完成；若超时，按任务状态机安全终止并记录。
4. 停止主服务。
5. 停止广告文件生成、Excel 导出和其他会写数据库或正式文件的后台进程。
6. 确认没有 `pending`、`running` 的任务和未完成文件移动。
7. 确认只有 PostgreSQL 服务保持运行，Commerce Ops 相关写进程全部停止。
8. 记录统一的 `cutover_at` UTC 时间。
9. 再执行一次 WAL checkpoint 和最终一致性备份。

停写验收：

- 主服务端口不再接受业务请求。
- 调度器进程已退出，租约不会继续续期。
- 运行中任务数为 0。
- 数据库与正式文件目录在连续观察期内不再变化。
- 最终 SQLite 备份的哈希、行数和文件 manifest 已归档。

## 阶段 3：数据迁移

```text
最终 SQLite 一致性副本
        ↓
读取 Schema 与规范化数据
        ↓
PostgreSQL commerce_ops.app
        ↓
索引、外键、CHECK、权限和序列校正
```

执行顺序：

1. 使用 `commerce_migrator` 连接 `commerce_ops`，再次核对目标库和 Schema，禁止误连演练库或其他数据库。
2. 在事务边界内创建 `app` Schema 对象；DDL 使用 F3 已验证的 PostgreSQL 转换结果，不直接执行 SQLite migration SQL。
3. 按 F3 拓扑顺序导入表数据，保留 UUID、时间、状态、软删除和文件关联。
4. JSON 文本逐行解析后写入 `jsonb`；任何无效 JSON 立即中止。
5. 0/1 布尔、日期、UTC 时间、bigint 和 UUID 按 F3 规则转换。
6. 创建外键、显式索引、部分唯一索引和 CHECK 约束。
7. 将两个 identity 表的序列重置到当前最大 ID 之后：`mabang_filter_option_cache`、`scheduled_export_run_events`。
8. 应用 `ALTER DEFAULT PRIVILEGES` 并确认 `commerce_app` 获得表 DML 和序列使用权。
9. 执行 `ANALYZE`，让查询规划器获得新数据统计信息。
10. 生成迁移结果报告，不记录密码、完整账号、文件绝对路径或业务明细。

迁移脚本必须具备：

- 目标数据库和 Schema 硬性守卫。
- 迁移批次 ID 与统一 `cutover_at`。
- 参数化写入与事务控制。
- 可重复演练，但正式库导入前要求目标为空或处于明确的可重建状态。
- 失败即停止，不使用假数据填补失败记录。

## 阶段 4：数据校验

### 4.1 结构校验

至少比较：

- 表数量：15。
- 字段数量：222。
- SQLite 索引 45 与 PostgreSQL 预期索引 47 的已解释差异。
- 外键数量：14。
- PostgreSQL CHECK 约束数量和定义。
- 主键、唯一键、部分唯一索引、删除动作和 identity 序列。
- `commerce_app` 权限边界。

### 4.2 数据校验

对每张表比较：

- 行数。
- 主键集合哈希。
- 全行规范化哈希。
- 唯一键冲突数。
- 关键列 NULL 数量。
- 状态分组数量。
- 最早、最晚时间。
- JSON 有效性。
- 外键孤儿数量。

### 4.3 重点业务校验

马帮和调度：

- `mabang_account_profiles`
- `mabang_filter_option_cache`
- `scheduled_export_tasks`
- `scheduled_export_runs`
- `scheduled_export_run_events`
- `scheduler_leases`

文件：

- `export_files`
- `managed_files`
- `file_lifecycle_scans`
- `file_lifecycle_items`
- `file_lifecycle_protected_files`
- `file_quarantine_records`
- 文件 ID、任务 ID、运行 ID、相对路径、大小和 SHA-256 关系
- 物理文件本体哈希不得发生变化

审计与配置：

- `operation_audit_events`
- `dingtalk_robot_configs`
- `schema_migrations`

当前系统没有标准订单表、库存快照表、AI 分析结果表或 Prompt 版本表。因此正式迁移不能宣称已校验这些不存在的数据。进入 G 阶段后，新表必须加入 F3/F4 同等级别的结构、行数和哈希校验。

### 阶段 4 Go/No-Go

仅当以下全部通过才可进入切换：

- 全部表行数一致。
- 全行与关键字段哈希一致。
- 外键孤儿为 0。
- 文件 metadata 与物理文件 manifest 一致。
- 应用角色可完成所需 DML 且不能执行 DDL。
- 两个 identity 序列下一值安全。

任何不可解释差异都必须回到 SQLite 生产状态，不能人工修改 PostgreSQL 数据后继续切换。

## 阶段 5：切换

### 5.1 只读冒烟

1. 保留 SQLite 最终快照不变。
2. 在维护状态下，将候选环境配置设为 `DATABASE_PROVIDER=postgres`。
3. 使用 `commerce_app`，不得使用 `postgres` 或 `commerce_migrator` 运行应用。
4. 先启动主服务，不启动调度器。
5. 执行只读页面/API 冒烟：任务列表、执行记录、文件列表、审计、账号脱敏读取。
6. 验证链接竞品、关键词竞品和广告入口加载，不调用危险外部操作。
7. 验证文件下载只根据文件 ID 和相对路径读取既有文件。

只读冒烟失败时，立即恢复 `DATABASE_PROVIDER=sqlite`，无需处理 PostgreSQL 新增数据。

### 5.2 受控写入

只读通过后执行一组可清理的受控操作：

- 创建并撤销测试配置。
- 执行 Mock 马帮任务。
- 生成测试 Excel 并核对元数据与文件哈希。
- 执行 Mock 钉钉通知。
- 执行 Mock AI 调用，确认不修改 Prompt 或算法。
- 核对审计记录和事务回滚。

受控写入通过后才允许解除维护状态。

### 5.3 恢复服务

1. 启动主服务并保持调度器关闭。
2. 开放人工操作，观察首批真实写入。
3. 确认任务、文件、审计和 API 正常后启动唯一调度器实例。
4. 核对下一次执行时间，避免为停机窗口重复补执行。
5. 确认没有旧 SQLite 调度器进程仍在运行。

切换验收覆盖：

- 链接维度竞品分析。
- 搜索关键词竞品分析。
- Lazada 广告分析代理、上传与 Mock 分析。
- 马帮账号、订单、库存、定时任务、钉钉通知和执行记录。
- 文件生成、查询、下载和生命周期关系。
- AI 网关调用与错误处理。
- 重启后任务和文件记录仍可读取。

## 阶段 6：观察期

### 前 24 小时

重点观察：

- HTTP 5xx、数据库错误、连接池超时、死锁和慢查询。
- 审计写入、任务创建、任务状态流转和文件关联。
- 调度器是否重复执行或漏执行。
- 文件生成、下载、大小和 SHA-256。
- PostgreSQL CPU、内存、连接数、磁盘和 WAL 增长。

建议每 2 小时核对一次核心表增量和任务状态；保留 SQLite 最终快照只读。

### 前 72 小时

- 覆盖每日和至少一次周/月规则的预览或 Mock 验证。
- 比较主要查询的 P50/P95 耗时。
- 检查 autovacuum、统计信息、索引命中率和数据库日志。
- 核对所有新增文件均有唯一文件 ID 和健康 metadata。
- 检查权限拒绝事件和异常重试是否符合预期。

### 前 7 天

- 完成一次 PostgreSQL 备份和隔离恢复演练。
- 汇总表增长、WAL 增长和备份大小。
- 复核索引是否围绕真实查询，避免无效索引堆积。
- 确认定时任务连续运行稳定。
- 决定是否结束高频观察，但 SQLite 快照继续按保留策略保存。

### 建议回滚阈值

任一项发生时进入人工回滚评估：

- 核心写入持续失败或出现不可解释数据差异。
- 同一计划任务重复执行。
- 文件 metadata 与物理文件发生不可修复的不一致。
- 数据库连接池持续耗尽。
- 关键 API 错误率或延迟显著高于 SQLite 基线。
- PostgreSQL 备份无法恢复。

# 第四部分 回滚方案

## 4.1 回滚级别

### A 级：解除维护前回滚

尚未开放真实写入时：

1. 停止主服务。
2. 恢复 `DATABASE_PROVIDER=sqlite`。
3. 使用最终一致性 SQLite 副本启动。
4. 运行完整性、文件 manifest 和页面回归。
5. 恢复主服务与唯一调度器。

这是最简单、数据零损失的回滚窗口。

### B 级：开放写入后回滚

PostgreSQL 已产生真实新增数据后，不能只改配置切回旧 SQLite，否则会丢失切换后的任务、审计和文件 metadata。必须：

1. 重新进入维护状态并停止所有写进程。
2. 以 `cutover_at` 为边界导出 PostgreSQL 增量记录。
3. 使用已演练的反向转换脚本，将新增/更新数据应用到 SQLite 恢复副本。
4. 对增量后的 SQLite 执行完整性、外键、行数、哈希和文件 manifest 校验。
5. 只有校验通过后，才将 `DATABASE_PROVIDER` 恢复为 `sqlite`。
6. 保存发生故障的 PostgreSQL 只读快照，供根因分析。

如果正式迁移前没有可演练的反向增量脚本，则开放真实写入后不具备低风险回滚能力，迁移必须判定为 No-Go。

## 4.2 代码回滚

- 使用独立迁移提交和发布标签。
- 通过 `git revert <migration-commit>` 创建可审计的反向提交，不使用破坏性 reset。
- 回滚前确认提交不包含迁移后的业务数据或配置密钥。
- 代码回滚与数据库 Provider 回滚必须配套，避免旧代码连接新 Schema。

## 4.3 配置回滚

- 恢复 Git 忽略的 SQLite 环境配置。
- 设置 `DATABASE_PROVIDER=sqlite`。
- 恢复 SQLite 数据库和文件根目录配置。
- 不删除 PostgreSQL 数据库，先转为只读证据。
- 重新运行 Doctor、测试和保护检查后再开放服务。

## 4.4 数据库回滚

- 优先恢复最终一致性 SQLite 副本，不直接使用可能在停机时未 checkpoint 的随意复制文件。
- 恢复后执行 integrity、foreign key、核心计数和 schema migration 检查。
- PostgreSQL 保留迁移批次、错误日志和 dump，禁止为了“清理”直接删除证据。

## 4.5 文件回滚

文件本体不迁入 PostgreSQL，迁移的是文件 metadata。因此：

- 正式切换期间不改变存储根目录和相对路径规则。
- 迁移前后校验 `export_files`、`managed_files` 与物理文件 SHA-256。
- 回滚时不盲目覆盖文件目录，只恢复缺失或哈希不一致的文件。
- PostgreSQL 期间生成的新文件必须与反向增量 metadata 一同回写 SQLite。
- 文件 ID、任务 ID、执行记录 ID 和相对路径必须保持原值。

# 第五部分 风险分析

| 风险 | 影响 | 防护 | 停止/回滚条件 |
|---|---|---|---|
| SQLite 0/1 转 PostgreSQL boolean | 状态反转或写入失败 | 逐列类型映射和 F3/F4 合约 | 出现非 0/1 值 |
| TEXT 时间转 `timestamptz` | 定时任务错时 | UTC 规范化并保留业务时区 | 时间哈希或下次执行不一致 |
| JSON 文本转 `jsonb` | 解析失败或键结构变化 | 逐行 JSON 校验和规范化哈希 | 任一无效 JSON |
| UUID 文本转原生 UUID | 非法 ID 无法导入 | 迁移前验证，不猜测转换 | 任一非法业务 UUID |
| identity 序列未重置 | 后续主键冲突 | 导入后按最大 ID 重置 | next value 不安全 |
| SQLite/PostgreSQL 排序规则差异 | 列表顺序或搜索不同 | staging 增加排序/大小写测试 | 关键查询结果不一致 |
| 马帮任务重复执行 | 重复导出和通知 | 单调度器、计划时间唯一键、停机核对 | 同一计划出现重复 run |
| 漏执行和错误补执行 | 经营数据缺口 | 记录维护窗口并人工审批补执行 | catch-up 结果不可解释 |
| 文件 ID 或路径变化 | 下载失败、历史断链 | 保留 UUID、相对路径和 SHA-256 | 文件关联不一致 |
| 应用误用迁移角色 | 权限过大 | 运行时仅允许 `commerce_app` | 应用连接用户不是 app role |
| PostgreSQL 连接池耗尽 | API 和任务阻塞 | 有界连接池、超时、监控 | 持续超时或连接泄漏 |
| 备份不可恢复 | 无法灾难恢复 | 迁移前和 7 天内恢复演练 | 恢复演练失败 |
| 迁移后直接切回旧 SQLite | 丢失新增数据 | 反向增量脚本和 cutover 时间 | 无增量回写能力时禁止开放写入 |
| 物理文件与 metadata 分离 | 数据库正确但文件不可用 | 双重 manifest 与下载回归 | 健康文件数下降 |

# 第六部分 未来云部署建议

## 6.1 三种形态比较

| 维度 | 本机 PostgreSQL | 服务器自建 PostgreSQL | 托管云数据库（如 RDS） |
|---|---|---|---|
| 成本 | 最低，使用现有电脑 | 云主机、磁盘和备份费用 | 通常最高，按规格、存储和备份计费 |
| 可用性 | 受关机、断电和本机故障影响 | 取决于服务器和自建运维 | 通常提供自动备份、监控和可选高可用 |
| 性能 | 本机访问延迟低 | 应用与数据库同地域/内网时稳定 | 规格可扩展，需关注网络和连接上限 |
| 维护 | 自己负责升级、备份和恢复 | 自己负责系统与数据库运维 | 厂商承担更多底层维护，仍需管理 Schema、权限和成本 |
| 安全 | 保持 loopback 最简单 | 使用私网、防火墙、最小权限和 TLS | 使用私有网络、安全组、TLS、审计和密钥管理 |
| 多人访问 | Web 服务需常开 | 适合团队远程访问 | 适合正式团队和更高可靠性要求 |
| 迁移难度 | 当前目标形态 | dump/restore + 配置切换 | dump/restore 或厂商迁移工具 + 网络白名单 |
| 文件存储 | 本地磁盘 | 独立磁盘或对象存储 | 数据库之外仍需对象存储 |

## 6.2 推荐路线

1. 当前阶段继续使用本机 PostgreSQL 做 staging、兼容测试和恢复演练。
2. 业务正式多人使用前，将应用与数据库放到稳定的服务器环境，数据库只通过私网访问。
3. 当数据成为正式经营依据、需要自动备份、时间点恢复或高可用时，再评估托管云数据库。
4. 无论选择自建还是托管，数据库端口都不因 Web 远程访问而公开到公网。
5. 图片、视频、Excel 和产品包文件迁往对象存储时，数据库只保存稳定文件 ID、相对对象键、大小和哈希。
6. 云迁移前核对数据合规、地域、备份保留、成本上限、出口流量和恢复目标。

## 6.3 建议恢复目标

正式经营前应由业务确认：

- RPO：最多可接受丢失多少分钟的数据。
- RTO：故障后多少时间内必须恢复。
- 备份频率、保留天数和异地副本。
- 每季度至少一次恢复演练。

RPO/RTO 未确认前，不应仅凭“云数据库有备份”判断系统已安全。

# 第七部分 下一阶段建议

数据库基础完成后，可进入 G 阶段“运营数据底座建设”，但仍应按小闭环逐步推进。

## G0：统一身份与主数据

- 平台、国家、店铺、类目。
- 产品 SPU、SKU、平台链接。
- 公司 SKU 与平台 Variation ID 映射。
- 币种、时区、数据来源和同步批次。

## G1：产品包与 SKU 体系

- 产品包原始导入与版本记录。
- 尺寸、材质、颜色、包装、安装和物流属性。
- 产品图片、说明书和素材文件 metadata。
- 产品知识字段与真实来源追溯。

## G2：订单与库存体系

- 原始采集层与标准订单、订单明细。
- 幂等唯一键和状态更新。
- 库存当前值、变动记录和必要快照。
- 店铺、产品、SKU、链接的稳定关联。

## G3：广告与链接指标体系

- Lazada、Shopee、TikTok 的统一广告日模型。
- 原始 Excel/API 批次与清洗结果。
- 计划、商品、关键词、花费、订单和销售额。
- 链接流量、转化与价格历史。

## G4：AI 分析与运营闭环

- AI 分析任务、输入数据版本、模型、Prompt 版本和输出摘要。
- 异常、建议、人工确认、执行动作和效果复盘。
- 不把固定公式交给大模型；利润、阈值和状态规则继续由规则引擎处理。

每新增一组持久化表，都必须同时补充：

- SQLite/PostgreSQL Schema 映射。
- Provider Repository 合约测试。
- 唯一键、索引、时区和币种规则。
- 数据保留与归档策略。
- 行数、哈希和文件关联迁移验证。
