# PostgreSQL Readiness Report

## Scope and snapshot

This E2 report prepares a future migration; it does not install PostgreSQL, create PostgreSQL tables, connect a driver, dual-write, or modify formal SQLite data. The read-only snapshot was taken from the configured formal database on 2026-07-16 after `PRAGMA integrity_check = ok`.

## Current tables

All UUID-like `TEXT` primary keys should become PostgreSQL `uuid`; integer identity keys should become `bigint GENERATED BY DEFAULT AS IDENTITY`; ISO timestamp text should become `timestamptz`; calendar-only dates should become `date`; JSON text should become `jsonb`; 0/1 flags should become `boolean`; byte counts should become `bigint`.

## Type conversion details

### JSON text

Convert `at_mobiles_json`, `schedule_config_json`, `payment_date_config_json`, `filters_json`, `log_summary_json`, `metadata_json`, `scopes_json`, `summary_json`, `scope_errors_json`, `categories_json`, product import payload JSON, mapping JSON, validation JSON and issue value JSON to `jsonb`. Validate every source value with `json_valid` before export. Replace the current `LIKE` lookup against `export_files.metadata_json` with a JSONB containment predicate and an expression/index chosen from real query plans.

Product field override values and detail-field preferences are also JSON text and must become `jsonb`. Product identity is now the normalized pair `country_raw + sku_code_normalized`; PostgreSQL must preserve the corresponding composite uniqueness instead of reverting to a globally unique raw SKU.

### Date and timezone

Convert `*_at`, `lease_until`, and file-created/modified timestamps to `timestamptz`. Convert `payment_start_date` and `payment_end_date` to `date`. Keep `scheduled_export_tasks.timezone` as an IANA timezone string. Parse all existing ISO values as UTC; do not infer a timezone for malformed or timezone-free historical text without a reconciliation exception.

### Boolean fields

Convert account/DingTalk/task flags, lifecycle `truncated`, `suggest_quarantine`, and `suggest_cleanup` from checked 0/1 integers to `boolean`. Reconcile with `value IN (0,1)` before import.

### Enums and checks

Keep current status/type checks as PostgreSQL `CHECK` constraints in the first migration. Native enums can wait until values stabilize. Preserve length checks for deletion actor/reason and 64-character SHA-256 checks.

## SQLite dialect inventory

- `PRAGMA busy_timeout`, `foreign_keys`, `journal_mode=WAL`, `table_info`, and `integrity_check`.
- `BEGIN IMMEDIATE` for write serialization.
- `INSERT OR IGNORE` for filter cache deduplication.
- `ON CONFLICT ... DO UPDATE` with `excluded` for scheduler leases.
- `datetime('now')` in historical migrations.
- `INTEGER PRIMARY KEY AUTOINCREMENT` in historical DDL.
- positional `?` placeholders and synchronous prepared statements.
- 0/1 integer booleans and JSON stored as `TEXT`.
- partial unique index for non-null `request_key`.

Runtime-only dialect operations are now located under `lib/data/sqlite`; `scripts/doctor.mjs` remains an infrastructure-only integrity probe. Business services use repositories and do not execute SQLite statements.

## Upserts and transactions

- Filter option caching uses ignore-on-conflict semantics across the composite option key.
- Scheduler lease acquisition uses one-row upsert followed by owner verification.
- Export idempotency depends on partial unique `request_key`; run uniqueness depends on `(task_id, scheduled_run_at)`.
- Task soft-delete/restore, run claims, cache replacement, lease acquisition, lifecycle completion, managed-file registration, and quarantine persistence require atomic transactions.
- PostgreSQL adapters must use explicit transactions and row/advisory locks where the current `BEGIN IMMEDIATE` serialized writers. Do not weaken claim/lease guarantees merely to share a generic SQL string.

## Migration sequence

1. Freeze schema changes and create a verified SQLite backup plus file manifest.
2. Build PostgreSQL migrations from the seven SQLite migrations, preserving keys, checks, indexes, and delete behavior.
3. Create PostgreSQL adapters behind the existing Provider/Repository contracts; keep SQLite as the active provider.
4. Import reference/config tables: accounts and DingTalk configs, preserving encrypted bytes.
5. Import task/run/event history, then export/file and lifecycle relationships in FK order.
6. Import cache, leases only if still relevant, and audit history last.
7. Reconcile counts, IDs, FK orphans, status distributions, min/max timestamps, JSON validity, and sampled SHA-256 metadata.
8. Run read-only shadow traffic against PostgreSQL.
9. Enable bounded dual-write only after explicit approval; SQLite remains authoritative during observation.
10. Stop scheduler writers, drain active runs, perform final delta copy/reconciliation, switch the provider, and retain SQLite read-only for rollback.

## Dual-write and reconciliation

Dual-write order should be SQLite transaction first, PostgreSQL second with an outbox/retry record; never hide a PostgreSQL failure. Before cutover compare every table's row count, primary-key set digest, status/type grouped counts, null counts for relationship columns, min/max timestamps, and all FK orphan counts. For files compare metadata IDs, relative paths, sizes, and SHA-256; file bytes remain in file storage rather than PostgreSQL.

## Rollback

During dual-write, disable PostgreSQL writes and continue from SQLite. After cutover, stop all writers, point `DATABASE_PROVIDER` back to SQLite, restore any post-cutover delta from the write journal, start one scheduler instance, and re-run integrity plus business-count checks. Never run both schedulers against the same due tasks without a shared ownership strategy.

## Data not yet persisted as formal facts

The current database does **not** contain normalized Mabang orders, order items, inventory snapshots, competitor snapshots, keyword search results, normalized advertising metrics, or AI analysis results. Those require separately reviewed schemas after PostgreSQL is stable. Existing Excel, browser extraction, and in-memory responses must not be presented as if these facts were already joined or historically queryable.

## F0 entry criteria

- Choose PostgreSQL version and deployment location.
- Approve backup retention, encryption-key availability, downtime window, and rollback owner.
- Add a PostgreSQL provider in a separate node without changing the SQLite provider.
- Produce dry-run DDL and reconciliation scripts against test copies only.
- Do not begin formal data movement until all repository contract tests pass for both adapters.
